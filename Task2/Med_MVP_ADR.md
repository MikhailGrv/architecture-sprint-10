### <a name="_qmphm5d6rvi3"></a>**Решение**
Приведите диаграммы контекста и контейнеров в модели C4. Опишите там основные компоненты и интеграции всех элементов решения. 

Также опишите, какой логикой вы руководствовались в ходе принятия решений и выбора технологий. Не забывайте, что необходимо учесть все функциональные и нефункциональные требования.

1. В связи с планами компании (рост) требуется масштабируемое решение - микросервисы
2. Требуется обеспечить безопасность - разделяем на 2 зоны DMZ и LAN со строго ограниченным взаимодейтвием (только разрешенные)
3. Портал Клиента
   1. В DMZ разворачиваем Портал для Клиентов, который имеет независимый KeyCloack, API Gateway (ограничеывает запросы без авторизации), k8s для разворачивания сервисов, Кэш, СУБД
   2. Все Взаимодействия внутри Портала для Клиентов должны быть защищены Tls(1.3), mtls
   3. Хранение данных - храним персональную информацию - требуется шифрование СУБД и строгое ограничение доступа с аудитом
   4. Сервисы предоставляют информацию только относящуются к Клиенту (проверяю JWT)
   5. Портал также позволяет Лаборатории подключиться и передать результаты (авторизация и своя роль)
   6. Роли: клиент, лаборатория
   7. Портал не хранит данные по анализам, только передает Портал Сотрудников
   8.  Для взаимодействия обязательна Идентификация и Авторизация
4.  Мастер система по записям и клиентам - Портал Сотрудников. Клиент может подать заявку на изменение данных и запись. Портал получает сообщение, обрабатывает и подтверждает или отказывает - обеспечиваем консистентность данных/непротиворечивость
5. Портал для сотрудников
   1.  Портал для сотрудников аналогичен Порталу для колиентов по структуре, но размещен в зоне LAN, куда нет доступа из интернет и могут работать только авторизованные сотрудники
   2.  Авторизация Keycloack с данными из AD (подумать над доменной авторизацией)
   3.  Пользователь также получает JWT, а сервисы также поверяют валидность JWT и роли
   4.  Роли: 
       1.  Сотрудник ресепшен - видит все записи на ограниченный период (например +- неделя) с информаций о докторе, но без информации по клиентам (усложняем массовую учтечку данных). Может выбрать конкретную запись и только там увидит контакты клиента (Имя, отчество + тел, фамилию - вопрос для обсуждения - предатагается маскировать) для прозвона. 
       2.  Сотрудник ресепшен - может поискать клиента по ФИО + дате рождения и/или тел. и посмотреть записи клиента в целях консультации клиента
       3.  Сотрудник ресепшен - не может смотреть исторю болезни. Может видеть дату поступления анализов.
       4.  Доктор - видит свои записи, зайдя в запись видит ИО клиета, историю болезни, анализы
       5.  Доктор - редактирует историю болезни 
   5.  Хренение персональных данных - согласно заканодательству 152-ФЗ. Длительность хранения должна быть ограничена по недействующим клиентам 3мя годами (если не ошибаюсь)
6.  Добавляем сервисы Логирования, Аудита, Трассировки. 
7.  Маркирование данных можно проводить подходящей системой. Также, можно проверять передаваемые данные в Шине Событий
